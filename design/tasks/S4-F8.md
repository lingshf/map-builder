# S4-F8: the Pittsburgh buried-collision singleton (`osm:way/537242388`)

Owner: dev · sprint S5, **first task** (D148, D149) · after v0.5.0 (#75, 6535f38) · user requirement: collision must
be exact.

## Finding

`tools/floating_audit.py` (threshold 0.2 m) on the Pittsburgh CLI release package (`pittsburgh-0.5.0.mbmap`,
SHA-256 `BE4374B0…`, `package_id` `sha256:3124bbee…`) reports one `buried_collision` region:

| Field | Value |
|---|---|
| Location | cell at map (−551.5, 19.5), 1 m², one cell |
| Offset | −8.77 m (collision hit 8.77 m below the visible surface) |
| Object | `osm:way/537242388` = `bld_way_537242388`, class `building`, flat roof, eave 9.0 m (`inferred:default for building=yes`), ground slope 0.32 m |

The same object at the same XY was already present on main 6fc2f02, before #77. The Blender package (float32
geometry) does not report it. #76 called it an "audit-ray edge graze".

The offset is about the building height. At this cell the visual ray hits the roof, but the audit's collision ray
misses the roof and lands at ground level. Two causes are possible, and they need different fixes:

* **(A) Audit artefact.** The audit raster's own ray/triangle test misses at a shared roof edge or vertex (a
  tolerance or tie rule), while the package's real query hits the roof.
* **(B) Real collision defect.** The roof collision has a crack, a missing or degenerate-removed triangle, or a
  T-junction at that XY, so a real drone ray falls through to the ground inside the building.

## Step 1: root cause (required; post it in the PR before any fix)

1. Cast the **package's own query** downwards at (−551.5, 19.5) and on a ±5 cm grid around it (step 1 cm). Use
   `core/query.py`, the same watertight ray the simulator contract uses, in **both Python and the C# reader**.
   Report the hit object, Z and triangle index for every ray.
2. List the roof collision triangles of `bld_way_537242388` within 1 m of the point. Report their vertices, the
   shared edges, any T-junctions, and any triangle removed as degenerate (S4-COL-DEGEN `degenerate_objects`).
3. Run the audit's ray/triangle predicate on the same rays and state exactly where it differs from step 1.
4. Repeat steps 1–3 on the Blender package, and explain why it does not report the finding.

Conclusion: **(A)** if every step-1 ray hits the roof in Python and C#; **(B)** if any step-1 ray falls through.

## Change

* **If (A), audit only.** Make the audit's collision ray test use the same exact, watertight predicate as
  `core/query.py`, rather than its own tolerance. The rule for edges and vertices must be stated in the code and
  docstring (D127 readability). There is no generator change, and every package stays byte-identical.
* **If (B), generator fix.** Close the crack at its source, in the building roof or collision triangulation.
  Opening an exception or masking the finding is not allowed. Scope: only the stage that produced the crack.
