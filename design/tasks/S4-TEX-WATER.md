# S4-TEX-WATER: water and other landcover read correctly with textures on

Owner: dev · sprint S4 · lane C · D56, D86, D99 · closes S3-F13

## Background (measured)

With textures on, the Pittsburgh river looks green. The mean RGB of pixels x 600–700, y 500–540 in
`docs/demo/v0.4.0/pittsburgh-overview-v040.png` is **(124, 162, 144)**, so G > B. The untextured render gives
(132, 166, 198).

Root cause: the terrain is one mesh with one material, `MB Terrain`, that uses `terrain_grass.png` for every
landcover class (`core/textures.py:33`). The water vertex colour (0.05, 0.14, 0.24) is divided by the grass
mean albedo (0.161, 0.196, 0.05) (`core/uv.py:68`) and multiplied by a green pattern. The same applies to sand
and forest.

## Scope (D99)

Replace the grass pattern with a neutral, luminance-only terrain-detail texture, generated by
`tools/textures/make_textures.py` with a seed, dedicated to CC0, and documented in `LICENSE-textures.txt`.
Update its mean albedo. The terrain is not split by landcover, and the geometry does not change.

## Acceptance criteria

1. Re-render `pittsburgh-overview` with the S1-DEMOKIT cameras on the frozen Pittsburgh cache. In the region
   above, the textured render has **B ≥ G** and each channel within **30** of the untextured render
   (stretch: 15). Grass areas still show visible texture detail (state the standard deviation of luminance in a
   grass region, before and after).
2. The texture is greyscale (R = G = B per pixel) and its mean albedo is recorded, as asserted in
   `tests/test_textures.py`. The regenerated bytes equal the committed file (existing test).
3. D86 holds: `asset_notices` and NOTICES list the new SHA-256; the frozen v0.3.0 readers and the current C#
   reader still load the package (CI).
4. `.mbcol` and the heightfield are byte-identical to before (only GLB, manifest and NOTICES change).
5. Texture set still ≤ 2 MiB (counted test).

## Performance considerations

No geometry or stage change. Same image size, so GLB size changes by less than 50 KB.
