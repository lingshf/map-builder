# S5-F4: Blender integration, terrain vertex edit export

**Priority:** P1, correctness (D164). **Order:** after S5-F3, before S5-STYLE-PALETTE.
**Owner:** Developer (step 1 and any fix); QA (rerun and behavioral acceptance); Product/Design (classification).

## Finding

The QA rehearsal of #92 ran the headless Blender integration suite on main `f1178f8` with Blender 4.2.23:

```powershell
& 'C:\tools\blender-4.2.23-windows-x64\blender.exe' --background --factory-startup --python-exit-code 1 --python tests\blender\run_integration.py -- "$env:TEMP\map-builder-doc-integration"
```

It exits 1 with `FAIL terrain vertex edit exported` (`tests/blender/checks_core.py:308`). Runtime and tests are
identical to the base, so the failure predates #92. The check compares the top of the first `terrain`-class
collision object's AABB with the highest world-space vertex of the edited Blender terrain (tolerance 1 mm). If the
edited terrain height does not reach the exported collision, a drone could meet ground at the wrong height, so this
is treated as a collision and height correctness risk until step 1 shows otherwise.

## Step 1: read-only root cause (no edits)

Classify the failure as one of these, with evidence:

* **R (real defect):** an edited terrain vertex does not reach the exported `.mbcol` terrain, or the `.mbhf` derived
  from it, in the Blender path.
* **T (test artefact):** the export is correct, but the check measures the wrong thing. One **hypothesis, not a
  finding:** since #77, `bank:<id>` shore-ramp objects also have class `terrain`, so
  `next(e for e in col.objects if e["class"] == "terrain")` may select a bank object instead of the edited terrain.

Evidence required for either class:

* the selected collision object's name and AABB;
* the edited terrain object's name, its world-space maximum Z, and the edited vertex;
* the `.mbcol` terrain object for the edited terrain, with its AABB and a Python and a C# downward ray at the edited
  vertex's XY;
* the `.mbhf` value at the nearest node;
* the first main commit where the check fails. Use a bisect over merged PRs on main, in a temporary worktree,
  with no data changes.

Post the evidence on the S5-F4 PR or issue thread before any fix.

## Fix and acceptance

* **AC1.** The documented integration command exits 0 on Blender 4.2.23, on the merged main.
* **AC2 (R).** The edited terrain height reaches the `.mbcol` terrain and the `.mbhf` exactly, within the check's
  1 mm. Python and C# rays at the edited vertex agree. Any change to collision geometry or the classic output needs
  **explicit user approval** obtained by the Team Leader (G0, D145) and a rebaseline (S5-STYLE-BASE AC1, the G0
  bases).
* **AC3 (T).** The check selects the edited terrain object by identity, not by class order. A negative test shows the
  fixed check still fails when a terrain edit is really dropped. A test-only fix changes no package bytes; G0 shows
  this.
* **AC4.** CI time is unchanged: the Blender suite is not a PR CI job. QA reruns the command and gives a behavioral
  acceptance verdict.
* **AC5.** `docs/dev/README.md` drops the "known failure" note in the same PR. That PR also needs the
  Knowledge Lead's agreement, because the page is owned by DOC-DEV.
