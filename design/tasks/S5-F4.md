# S5-F4: Blender integration, terrain vertex edit export

**Priority:** P1, correctness (D164). **Order:** before S5-STYLE-PALETTE.
**Owner:** Developer (step 1 and fix); QA (rerun and behavioral acceptance); Product/Design (classification).

## Finding

The QA rehearsal of #92 ran the headless Blender integration suite on main `f1178f8` with Blender 4.2.23:

```powershell
& 'C:\tools\blender-4.2.23-windows-x64\blender.exe' --background --factory-startup --python-exit-code 1 --python tests\blender\run_integration.py -- "$env:TEMP\map-builder-doc-integration"
```

It exits 1 with `FAIL terrain vertex edit exported` (`tests/blender/checks_core.py:308`). The check compares the
top of the AABB of the **first** `terrain`-class collision object with the highest world-space vertex of the edited
Blender terrain (1 mm tolerance).

## Step 1: read-only root cause (done)

Classes: **R** = a real export defect (an edited terrain vertex does not reach the exported terrain collision or
the `.mbhf` derived from it); **T** = a test artefact (the export is correct, the check measures the wrong thing).

**Result (Developer, reported by the coordinator; D164): class T.**

* First bad commit: db9db44 (#77, shore ramps). Since #77, `bank:<id>` objects are also class `terrain`, and the
  check's `next(... class == "terrain")` can select one of them.
* The exported `terrain:grid` collision, the `.mbhf` and the GLB all match the edit.

**Evidence: pending capture.** The fix PR body records, measured as in AC2: the object the old check selected and
its AABB; the `terrain:grid` AABB; the edited vertex and its world Z; the Python and C# rays at its XY; the `.mbhf`
node values; and the bisect provenance (the commits tested, and the last good and first bad). Until then the class-T
result is the Developer's report as relayed by the coordinator.

## Fix and acceptance

* **AC1.** The documented integration command exits 0 with `OK: 0 failure(s)` on Blender 4.2.23, on the fix PR's
  exact head and again on merged main.
* **AC2 (what the check measures).** The check names its expected hit object, `terrain:grid` (the edited
  terrain's own export identity), and selects it by identity, not by class or list order. It then compares at
  matching coordinates:
  * **collision:** a downward ray at the edited vertex's XY hits `terrain:grid` within 1 mm of the vertex's world Z.
    A miss, or a hit on any other object, fails with that object named;
  * **heightfield:** at an actual `.mbhf` grid node covered by the edited area (or with the test vertex placed
    deliberately on a node), the node value equals the top of the exported `terrain:grid` at that node within
    1 mm. An uncovered (no-data) node is reported as "not covered" and fails; it is never compared as a height.
* **AC3 (positive and negatives).**
  * **Positive (the regression):** the edited `terrain:grid` is present and correct, but another `terrain`-class
    object (a `bank:<id>`) comes first in class order. The check **passes**. A bank's presence or order is not a
    defect.
  * **Negatives:** the check fails, naming the cause, when (a) the edit is stale or dropped (the exported
    `terrain:grid` lacks it); (b) `terrain:grid` is missing; (c) the collision ray at the edit XY hits another
    object.
* **AC4 (no package change).** The fix is test-only. Proof: the packages are built with a pinned clock and
  identically controlled inputs on the merge-base and on the head, then compared.
  * Pinned clock: the CLI uses `--created-utc 2026-11-20T00:00:00Z`; Blender uses the equivalent
    `created_utc="2026-11-20T00:00:00Z"` passed to `blender/bake.py` `export_baked`.
  * Repeatability first: two builds on one revision must give the same whole-archive SHA-256. Then base and head
    whole-archive SHA-256 must be equal.
  * If Blender cannot pin the clock, compare member by member instead. Every member must be byte-identical except
    `manifest.json`. The manifest is compared as JSON with only `created_utc` removed, and the package ID derived
    from the raw manifest is excluded with it.
  * G0 alone covers only the flight-data members and is not enough.
* **AC5.** QA reruns the full command and gives a behavioral acceptance verdict. The Blender suite is not a PR CI
  job, so CI time is unchanged.

The "known failure" note in `docs/dev/README.md` (added by #92) is **outside** this task's domain. After S5-F4
closes, the Knowledge Lead removes it in a DOC-DEV follow-up, citing AC1 on merged main.
