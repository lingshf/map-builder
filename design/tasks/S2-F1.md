# S2-F1: make the TLS-deadline test deterministic

Owner: dev · sprint S2 · **v0.3.0 blocker** · recorded in [S2-REVIEW](../reviews/S2-REVIEW.md)

## Problem

`tests.test_terrain_sources.RoundFourTest.test_stalled_tls_handshake_hits_deadline` is flaky.
It failed in the full local suite and in 2 of 15 isolated runs on main `2de9024`.

The test serves a real socket that sends one byte every 50 ms and expects the 0.6 s
`total_timeout` to fire. `DeadlineProbe.assert_armed` then requires `len(shutdowns) >= 1`.
Under CPU load the race between the dribble, the deadline timer and the shutdown call can go the
other way. A flaky test makes "CI green on the final head" (DoD 2) unreliable.

## Acceptance criteria

1. The test keeps its intent: a TLS handshake that keeps receiving bytes but never completes is
   cut off by the total deadline, and the socket is shut down.
2. The outcome no longer depends on scheduling. Use an injected or fake clock/timer, or a
   handshake stub the test controls, rather than real sleeps racing a real timer.
3. 50 consecutive isolated runs pass locally, and the full suite passes 3 times locally under
   parallel CPU load (for example, two suites at once). Record the commands and results in the
   PR body.
4. Reverting the deadline fix in the product code still makes the test fail. Show this once in
   the PR.
5. No wall-clock assertion is added (DoD 3).

## Performance considerations

The test stays ≤ 5 s, and should be faster than now, since it no longer waits on real 50 ms
ticks. The suite must not get slower.

## Conflict domain

Hard: `tests/test_terrain_sources.py`. If a timer seam has to be injectable, also the matching
`core/http.py` function; keep that change minimal and behaviour-neutral.
